## 一、對照 domi-trip-planner：要補的東西

### 先講結論

app 現在的「用講的改行程」只對應到 skill 的 A9（改行程）。skill 有四條線，另外三條 app 都還沒有：

| skill 的線 | 做什麼 | app 現在 |
|---|---|---|
| A 排新行程 | 問一輪，整趟排完，附池子、備案、要先訂的、須知 | 有，規則引擎排的，沒有備案和峰值 |
| B 健檢 | 貼一份別人排的行程，照八層從上游查起，指出哪一層壞了 | 沒有 |
| C 旅途中 | 早上問精力、出狀況照事先寫好的條件句換、晚上問一句 | 只有「今天累」按鈕 |
| D 旅後回顧 | 三張照片、每晚那一句串起來、三條「下次要記得」 | 有去過的和那一句，沒有「下次要記得」 |

我覺得最值得搬的是 C 的想法：**出狀況時不要讓 AI 臨場發揮，讓它去對出發前就寫好的條件句。** skill 的說法是「讓冷靜的人替現場的人做決定」。這樣 AI 在首爾街頭只做比對，不做創作，比較不會講錯，也比較省錢。

### 行程裡要多出來的選項

上一份的選項表有些要改，有些要新加：

| 選項 | skill 怎麼定 | app 要怎麼做 | 取代上一份的 |
|---|---|---|---|
| 錨的種類 | 硬錨（不可替代、有時刻）、軟錨（不可替代、只指定半天）、偽錨（可替代卻有時間鎖）、填充（進池子） | 每一站多一欄 `anchor`。硬錨就是上一份說的「鎖住」，多一個時刻；軟錨可以有兩個候選半天 | 取代 `lock` |
| 重／輕 | 要一直動腦超過約一小時的算重；每半天最多 1 個重、每天最多 2 個，兩個重中間夾輕的 | 現在用大站／小站（花半天與否）代替。兩者不同：逛街可以花半天但是輕的，博物館一小時但是重的 | 新加 |
| 峰值 | 每趟 1–2 個，最直接回應「這趟想怎樣」的那一刻；不放第一天、前後排輕、有天氣風險給換日備案 | 每一站多一個「峰值」標記，AI 改行程時不准隨便動 | 新加 |
| 備案 | 只替有風險的錨點寫，一個錨點一條；格式是「如果＋看得見的訊號，就＋具體動作」，訊號要有門檻（降雨機率超過 60%、排隊超過 40 分鐘） | 存成每一站的一個欄位。旅途中使用者說「下雨了」，AI 先找這條 | 新加 |
| 順路可去 | 每個半天 2–3 個候選，至少一個室內、一個可以坐，標 ☔ 雨備 | app 有這個池子，要改成跟著半天走，並標室內、可坐 | 改 |
| 結尾 | 最後半天輕、好、近：行李寄存、伴手禮前一天買、只排一件靠近回程路上的事 | 規則引擎補一條 | 新加 |
| 要先訂的 | 多一個「決定截止日」，過了就停止比價 | 檢查表上每一項多一個日期 | 改 |
| 否決清單 | 每人「這趟絕對不想做的事」 | 對到 app 的「以後都不排」和「絕對不吃」，但 skill 是每趟問一次 | 改 |
| 規劃者類型 | 研究家、做夢家、焦慮比價者、外包者 | 影響 AI 一次給幾個選項、要不要直接定死。可以從回答語氣推，不用設定頁 | 新加 |

多人的部分（每人分開回答、共同／分開時段、會合點、逾時規則、每天的決定者）skill 寫得很完整，但產品定稿把「旅伴各自填偏好」放第二版。第一版先不做，記在這裡。

### 會跟 AI 講的話，多出來的幾類

| 情境 | 例句 | AI 該做的 |
|---|---|---|
| B 健檢 | 「這是我朋友在 Notion 排的，你幫我看」（貼一段） | 照八層查，找到第一個壞掉的層就停，說證據和改法；要的話轉成 app 的格子 |
| C 早上 | （打開 app）「今天精力比昨天高還是低？」 | 低就給降級版的今天：重的降成輕的、軟錨挪後、從池子挑可以坐的，峰值不動 |
| C 出狀況 | 「下雨了」 | 先找那一站的備案條件句；沒有才臨場想，順序是換日、換時段、換地點、放棄 |
| C 錢已經付了 | 「票都買了，還是去吧」 | 看放棄條件，不被已付的錢綁住；決定權在他 |
| C 晚上 | 「今天最想跟別人講的一件事？」 | 存成那一句 |
| D 回來 | 「回來了」 | 串起每晚那一句、問三條「下次要記得」，下次開一趟時當預設 |

「早上一問」和「晚上一問」要不要用通知推，要多米決定。我的看法是可以做，但只在旅途中、一天最多各一次、可以關。它問的是精力，不是「你今天還沒打開 app」，跟產品定稿禁止的罪惡感提醒不一樣。

### 改行程時的規則，多出來的

1. 使用者要加一站，先數那天的重刺激。超過上限就問要拿掉哪個，或把新的放進下次再來。
2. 只改被動到的那一天，回覆不要整份重貼。
3. 每次改完跑一次規則檢查（skill 最後那張 14 條的清單）。app 現在的 `warnings()` 只檢查一天幾個大站，要擴充。撞到的用一句話提醒，不擋。
4. 峰值、硬錨、自己加的站，AI 要動之前先問。
5. 換一個：一次三個，每個一句為什麼對準這趟目的，最多三輪；第三輪還不滿意，建議先留白、到現場從池子挑。app 已經有三輪上限。

## 二、要接哪家的哪個模型，一趟花多少

先說利益關係：我是 Anthropic 的 Claude，推 Claude 對我有利。所以下面也列了另外兩家的價格，並寫了怎麼用同一份題庫自己比。

### 結論

| 用在 | 推薦 | 理由 |
|---|---|---|
| 排整趟（一趟一次） | Claude Opus 5.5 | 一趟只叫一次，約 NT$12。這是使用者決定放不放心的那一刻，不在這裡省 |
| 用講的改（一趟幾十句） | Claude Haiku 5.5，題庫沒過再換 Claude Sonnet 5.5（effort 設 low） | 句數多，價差會放大到吃掉一趟的收入，算式在下面 |
| 地點查證 | 不用大模型，用 Google Places | HANDOFF 7-3 已經算過，這是整趟最貴的一項 |

判斷 Haiku 夠不夠用的方法：拿 `docs/跟AI討論行程的情境清單.md` 第二節的例句當題庫，挑 20 句，Haiku 和 Sonnet 各跑一次。改對 18 句以上就用 Haiku。HANDOFF 第 4 階段的驗收本來就是「十句至少九句改對」，標準一樣。

app 這邊已經有一道保險：AI 回來的每一個改動都要過 `applyOps` 檢查，改不了的會擋下並說原因，改了也能復原。所以便宜模型偶爾給錯指令，代價是一句「沒做成」，不會把行程弄壞。

## 三、為什麼不用「問 AI＋記在 Notion」就好

### 一句話

問 AI 拿到的是一段文字，排完之後核對、整理、到了現場查怎麼走，全部還是自己來。蘿蔔旅行把這三件做掉了。

### 拆開來看

| | 問 AI＋記在 Notion | 蘿蔔旅行 |
|---|---|---|
| AI 給的東西 | 一段文字，你自己複製貼上 | 每一站是一格資料：地點、時段、怎麼去、花費、須知、要不要先訂 |
| 改一個地方 | 改了第三天，第五天提到的訂位、花費、檢查表不會跟著動，要自己對 | 改一站，地圖、站間交通、花費、檢查表一起變 |
| AI 答應做不到的事 | 會。它說「好，幫你排進去了」，其實那天已經有兩個大景點、或那間店週一休息 | 改動要過規則檢查，做不到的會擋下來說原因；改錯可以復原 |
| 店存不存在 | 自己查。上一份文件引的調查：六分之一用 AI 排旅行的人被推薦過不存在的地方 | 地點要查得到地圖才進行程；每一站標核對過、估的、還是沒核對 |
| 記得你 | 每開一個新對話要重講一次習慣（有些聊天 app 有記憶，但不會照你的習慣套排法規則） | 平常的我、以後都不排、過敏告知卡，每一趟自動帶入 |
| 排法 | 通常是景點清單塞滿每一天 | 一天最多兩個大站、第一天和最後半天輕、每天留白、同半天同一區；skill 的峰值、備案、重輕交替會接著補進來 |
| 在首爾現場 | Notion 沒網路時只看得到開過的頁；沒有韓文地址放大給司機看；AI 不知道你現在第幾天幾點 | 離線看得到全部；韓文名稱和地址、一鍵 Naver；AI 知道現在幾點，只動今天還沒過的時段 |
| 要會什麼 | 要會寫提示詞、會整理 Notion | 回答幾題 |

### Notion 贏的地方

這要講清楚，不然判斷會偏：

- 自由。想放什麼就放什麼，表格、連結、截圖都行
- 共編。兩個人一起改同一份，蘿蔔旅行第一版不做
- 不用錢
- 研究家型的人（看攻略看到半夜還開心的那種）本來就喜歡自己整理，Notion 對他們剛好

所以蘿蔔旅行的對象，是 skill 裡說的外包者和焦慮比價者：想要一份能照著走、而且不用自己再核對一次的行程。研究家不是我們要搶的人。

### 由這個差異推出來的兩個功能

1. **貼進來健檢**：讓用 Notion 或聊天 AI 排好的人，把行程貼進 app，跑 skill 的 B 線，指出哪一層有問題，再轉成 app 的格子。這是把 Notion 使用者接過來的入口，也直接示範了上面那張表的差別
2. **傳給旅伴看**：產生一張圖或一段文字丟 LINE（上一份需求文件的第 5 點）。補上 Notion 共編那一塊最常用的部分，又不用做帳號

## 四、AI 能改哪些東西：權限怎麼開

### 一句話

AI 永遠碰不到資料本身。它只能回一張「我想做這幾件事」的清單，app 照一張白名單一條一條檢查，合格的才套上去，而且能復原。要開放 AI 改更多東西，就是在白名單上多加一種動作，並替它決定權限等級。

這套機制現在已經在跑：AI 回 `{reply, ops}`，`applyOps()` 只認得七種 op，不認得的不做，碰到過去時段和拔起來的站會擋（昨天加的）。往下只是把它擴大。

### 三個權限等級

| 等級 | 意思 | 適合什麼 |
|---|---|---|
| 直接改 | AI 說了就改，對話裡列出改了什麼，一個復原退回整批 | 改錯了代價小、退回容易的 |
| 要確認 | AI 只能提議，app 跳一張「改前／改後」的卡，使用者按「套用」才改 | 影響整趟、或會被當成以後預設的 |
| 不准 | 不管 AI 回什麼都不做 | 使用者自己的紀錄、核對過的事實、錢 |

### 每樣東西放哪一級（我的建議）

| 東西 | 等級 | 理由 |
|---|---|---|
| 站的位置、加站、拿掉、換一個、留白、上午下午對調 | 直接改 | 現在就是這樣，拿掉的進下次再來，不會不見 |
| 站與站之間的交通方式 | 直接改 | 只影響估算 |
| 站的一行備註（「19:00 已訂」）、備案條件句 | 直接改 | AI 寫的標「AI 寫的」 |
| AI 加的站的說明和須知 | 直接改 | 只限 AI 自己加的站，而且標「未核對」 |
| 檢查表：新增一項、勾掉一項 | 直接改 | 可復原 |
| 這趟的名稱 | 直接改 | 純文字 |
| 檢查表：刪掉一項 | 要確認 | 刪掉的使用者可能沒注意到 |
| 這趟的條件：日期、天數、班機、人數、住哪一帶 | 要確認 | 會牽動整趟，受影響的站要挪 |
| 這趟特別的地方（多咖啡廳、吃好一點） | 要確認 | 卡片上兩顆鈕：「只這趟」「以後都這樣」 |
| 平常的我、以後都不排、過敏、絕對不吃 | 要確認 | 會被所有以後的行程當預設，過敏還牽涉安全 |
| 峰值、硬錨、自己加的站 | 要確認 | 使用者自己釘的東西 |
| 拔起來、那一句、照片 | 不准 | 那是他自己的紀錄 |
| 自己記的花費 | 不准 | 錢的紀錄 |
| 核對過的事實：地址、營業時間、來源、核對日期 | 不准 | 只有查證那條流程能寫，AI 一改就失去「核對過」的意思 |
| 須知資料包、要先訂的「怎麼訂」 | 不准 | 人工整理、附來源的內容 |
| 介面上的文字（按鈕、標題、說明） | 不准 | 這是程式的一部分，由我們改程式碼發新版，不讓執行中的 AI 改 |

### 程式上怎麼做

1. **一張權限表。** 每一種 op 寫明它的等級，例如 `move` 直接改、`setHabit` 要確認、`pull` 根本不存在。AI 回了表上沒有的 op，照現在的做法忽略。新增能力就是：加一種 op、在表上給它等級、寫它的檢查、補測試
2. **每一種 op 自己的檢查。** 跟 `chatFrozen()` 一樣，套用之前先看能不能動：目標存在嗎、時段過了嗎、是不是使用者自己的紀錄、文字長度有沒有超過上限
3. **「要確認」的 op 先不套用。** 存成一張待確認卡，畫面上列改前和改後，按「套用」才走 `store.act(undoable: true)`，按「不要」就丟掉
4. **AI 寫的文字一律標出來。** 寫進資料時加 `ai: true`，畫面上顯示「AI 寫的」或「未核對」，跟產品鐵則「AI 加的寫 AI 加的」對齊
5. **一整批算一步復原。** 一句話改了五站，按一次復原全部退回。現在就是這樣
6. **提示詞只列這次用得到的 op。** 列全部會多花 token，也讓模型分心。例如還沒出發就不列跟「今天」有關的
7. **後端用結構化輸出。** 接 Claude 時用 `output_config.format` 給一份 JSON schema（Opus 5.5 和 Sonnet 5.5 不能強制呼叫某個工具，用結構化輸出），回來的格式一定對。內容合不合理還是由 app 的檢查決定，因為資料在手機上，只有 app 知道現在行程長怎樣
